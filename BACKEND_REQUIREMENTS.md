# Backend Requirements — Admin Panel Redesign

Separate from `ADMIN_PANEL_REDESIGN.md` (open items only; finished work is in `task_Logger.md`). This file is a punch list of backend
work needed to make fabricated/demo data on the redesigned admin pages real. Items marked **DONE** are
implemented (2026-10-05); the rest are not — no backend files are touched for those without your explicit go-ahead.

Format per item: **what's needed**, **why** (which page/field needs it), **rough shape** (endpoint/column/migration).

---

### Orders domain

1. **PARTLY DONE — Customer identity on an order.** Done: `orders.warehouse_id` (real warehouse name on Order detail); customer name/phone now come from the order's own address (`order_addresses.full_name/phone`), no auth-service call. Still open: picker and rider (still fabricated; rider could come from delivery-service assignments). Order count and spend per customer now show on Order detail, with a "View customer" link (2026-10-06). Original note: Order/OrderDetail/Overview/Movements/Reservations all show a fabricated customer name, phone, warehouse, picker and rider (`lib/orderDemoData.js`) because `order-service` only stores `user_id` with no name/phone, and there's no warehouse/picker/rider assignment on an order at all. Shape: either a read-only join to `auth-service` users, or denormalized columns on `orders` (`warehouse_id`, `picked_by`, `assigned_rider_id`) plus a cross-service user lookup for name/phone.
2. **DONE — Date-scoped aggregates** (`GET /orders/admin/stats?warehouse_id=&days=&tz=`; see `ORDERS_API_PLAN.md` §3). Original note: No endpoint returns today's revenue, order count, average delivery time, or cancellation %. Blocks Overview's 4 top stat cards (currently `lib/overviewDemoData.js`). Shape: `GET /orders/admin/stats?date=` returning `{revenue, orders, avgDeliveryMinutes, cancelledPct}`.
3. **DONE — Per-day order-count time series** (`perDay` in the same stats endpoint). Original note: No endpoint buckets orders by day. Blocks Overview's "Orders per day" chart (currently fabricated). Shape: `GET /orders/admin/daily-counts?days=7|30`.
4. **DONE — `GET /orders/admin/all` status filter now accepts a single value, comma list or array** (and `warehouse_id` is required, unless `user_id` is given: then it lists that one customer's orders across warehouses, used by the Customers page "View orders"). Original note: A design group like "In store" (CONFIRMED + AWAITING_CUSTOMER_CONFIRMATION + READY_FOR_ASSIGNMENT) can't be paginated server-side — `use-order.js`'s `useAdminOrders` works around it by firing one request per status and merging client-side. Shape: accept `status` as a comma-separated list or array.
5. **Order↔promotion attribution.** No link between an order and the promotion applied to it. Blocks Promotions page's "Orders with a promo %" and "Discount given today ₹" (currently fabricated). Shape: an `order_promotions` join table or a `promotion_id` column on `orders`.

### Inventory domain

6. **DONE (2026-10-06) — `GET /stock-reservations` filters: `status=` (ACTIVE / CONFIRMED / RELEASED / EXPIRED, case-insensitive), `warehouse_id=`, `search=`** (order id, or product name via product-service's `GET /product-variant/variants/search`, capped at 200 variants; 400 on a bad value). The response also carries `statusCounts` (per status, within the warehouse/search filter), backed by an index on `(status, created_at)`. The list is now ADMIN / SUPER_ADMIN / OPS_STAFF only; the other three reads need a login (order-service forwards the caller's token). The Reservations page uses all of it, nothing is page-only any more. **Still open:** inventory-service `authenticateToken` lets every role through (`role === "ADMIN" || "SUPER_ADMIN"…` is always true), so the reservation POST/PATCH routes accept customers; that is relied on today because order-service creates and releases reservations with the customer's token. Fixing it needs a service-to-service token first. Not covered by search: the quantity/unit part of a variant name (e.g. "500 g"). Original note: the status pills only narrowed whatever page was already loaded, not the full result set.
7. **DONE (2026-10-06) — `GET /stock-movements?type=&warehouse_id=`** filters on movement type (STOCK_IN / SALE / ADJUSTMENT / DAMAGE / RETURN) and warehouse, combined with `page` / `limit`; pagination totals reflect the filter. Bad values return 400. The Movements page sends both to the server (page resets to 1 on change); its search box is still client-side because variant names live in product-service. Not done: a date filter (the page has no date control). Original note: **`GET /stock-movements` had no type/warehouse/date filter.** Same page-only-filter limitation as above, on Movements.
8. **No global (all-warehouse) stock aggregate.** Low/out-of-stock counts are only per-warehouse (`GET /inventory/warehouse/:id`); a true cross-warehouse count needs an N+1 fan-out we deliberately avoided. Blocks a real "Items low or out of stock" figure on Overview (currently fabricated in `overviewDemoData.js`). Shape: `GET /inventory/admin/stats` returning global low/out-of-stock/reserved counts.
9. **DROPPED — `DeliveryZone` will not get a `warehouse_id`** (decided 2026-10-06). The fabricated Warehouse column was removed from the Zones table. Original note: The Zones page's Warehouse column was fabricated (reused `getDemoWarehouse`). Shape: add a `warehouse_id` FK column + migration.
10. **DONE (status) — `Warehouse.operational_status`** (OPEN / PAUSED / MAINTENANCE / SETTING_UP, default OPEN) added 2026-10-06; Dashboard Warehouses card and the Warehouses page use it. Per-warehouse order count and pick+pack time were dropped from the card (decided 2026-10-06). Original note: **`Warehouse` has no operational-status field.** Only `is_active` (boolean) exists — no Open/Paused/Maintenance/Setting-up state, no per-warehouse order-count or pick+pack-time metric. Blocks Overview's Warehouses panel (currently fabricated per-id in `overviewDemoData.js`). Shape: an `operational_status` enum column, plus a metrics source (could derive order-count/pick-time from real data once #1's warehouse-on-order link exists).

### Customers domain

11. **DONE (2026-10-06) — admin customer list.** `GET /auth/admin/users?search=&status=active|blocked&joined_days=&page=&limit=` (auth-service; ADMIN / SUPER_ADMIN) returns customers with addresses and `counts` {total, newThisWeek, blocked}. Order count, spend, last order and recent orders come from `GET /orders/admin/customer-stats?user_ids=1,2,3` (order-service), which also returns store-wide `summary` {ordered_this_month, repeat_customers, customers_with_orders}. The Customers page uses both. Block / unblock: `PATCH /auth/admin/users/:id/status` `{ is_active }` (customers only; revokes refresh tokens and sessions on block; login and token refresh refuse inactive users). Not done: a "repeat customers" filter. Original note: **No admin customer-list/search endpoint anywhere.** `auth-service` has no way to list/search/paginate users as an admin. The entire Customers page is fabricated (`lib/customersDemoData.js`). Shape: `GET /auth/admin/users?search=&page=&limit=` returning name/phone/email/order-count/spend/status, likely needs a join against order-service for order-count/spend or a periodic rollup.
12. **No admin endpoint to list/count locked staff accounts.** Blocks Overview's "Locked staff account" card (currently fabricated). Shape: `GET /auth/admin/users?locked=true` (#11 now exists, but only returns role CUSTOMER and has no `locked` filter yet).

### Settings domain

13. **PARTLY DONE (2026-10-06) — `config-service` backend.** `GET /config` returns `{ general, orderRules }` (saved values over defaults) and `PATCH /config/:group` (`general` or `orderRules`) saves a partial update atomically; both are ADMIN / SUPER_ADMIN only, behind the gateway (`/config`, port 3007, table `settings`). Not done: the Settings page still uses local state (General and Order rules tabs can now be wired); the Notifications tab has no backend (those are per-admin "email me" prefs and `notification-service` is empty); order-service still hard-codes its 15-minute timers, so the order-rule values are stored but nothing reads them yet. Original note: **`config-service` had no models or routes and wasn't registered in the API gateway.**
14. **No update-profile endpoint.** Settings' "My account & security" Save button can't persist name/email/mobile edits (only `GET /auth/profile` exists). Shape: `PUT /auth/profile`.
15. **`POST /auth/logout/all` is registered without a leading slash** (`router.post('logout/all', ...)` in the auth routes file) — didn't touch it per the no-backend-changes rule, but it should be checked; it's why Settings' "Sign out everywhere else" button isn't wired to it.

### Delivery partners domain

16. **PARTLY EXISTS — delivery-service has a `DeliveryPartner` model and admin endpoints, but almost nothing the new Delivery partners screens need.** What's there: `POST /delivery-partners`, `GET /delivery-partners/:id`, `PATCH /:id`, `PATCH /:id/location`, `/:id/activate`, `/:id/suspend`, `GET /delivery-partners` (only the *available* partners for a warehouse via `x-warehouse-id`), `DeliveryPartnerZone`, status history, assignment / attempt / handover tables, and `POST /handle-orders/assignments/*` for dispatchers. What's missing is listed in items 17–28. Until then the admin pages (`/dashboard/delivery-partners`, `…/new`, `…/applications/:id`, `…/:id`) and the partner screens (`/partner/*` phone, `/partner/apply/*` sign-up) run on demo data from `client/src/lib/partnerDemoData.js`, marked in the UI. Buttons that need new endpoints show a "not wired up yet" toast. The Overview "Partner applications to review" card and the sidebar badge are still fabricated.
17. **DONE (2026-10-07) — partner list with identity.** `GET /delivery-partners/list?search=&zone_id=&status=ACTIVE|SUSPENDED|INACTIVE&online=true|false&page=&limit=` (delivery-service; ADMIN / SUPER_ADMIN / OPS_STAFF via `authenticateToken`) returns `{ partners, pagination }`: name, masked phone (last 3 digits), zone `{id, name}`, vehicle, `is_online` / `online_since`, `current_active_orders / max_active_orders`, `delivered_today`, status. `search` matches name, phone or vehicle number. Name and phone are a copy on the partner row (new nullable columns, accepted by `POST` and `PATCH /delivery-partners`); the model's default scope hides them from the unauthenticated `GET /`, `/zone` and `/:id`. The Partners tab now reads it. Not done: `is_online` / `online_since` are never set (needs partner sign-in, item 23), so every partner shows Offline; `delivered_today` counts COMPLETED assignments by `updated_at` (no `completed_at` column) since server-local midnight; existing partner rows have no name or phone until they are edited; `POST /delivery-partners` still fails because `authenticateToken` sets `req.user = decoded.user`, which is `undefined` (see backend/CLAUDE.md); the partner detail page is still demo data and opens the wrong demo partner for a real id. Original note: **`GET /delivery-partners` returns only available partners and has no name or phone** (the row holds `user_id`; identity lives in auth-service).
18. **Partner summary counts.** One call for the four stat cards and the sidebar badge: applications waiting for review (+ age of the oldest), active partners (+ number of zones), online now (+ orders in progress), suspended (+ suspended this week). Shape: `GET /delivery-partners/admin/summary`. Also unlocks Overview's "Partner applications to review" card.
19. **Applications workflow (new table + endpoints).** No concept of an application exists. Needs `delivery_partner_applications` (name, phone, preferred zone, vehicle type/number, source `SELF` | `ADMIN` + `created_by`, status `NEW` | `UNDER_REVIEW` | `CHANGES_REQUESTED` | `APPROVED` | `REJECTED`, `submitted_at`, reviewer, note, reference like `FR-P-2231`) and: `GET /delivery-partners/applications?status=&zone=&page=`, `GET …/:id`, `POST …` (self sign-up and admin "Add partner"; admin-created ones also send an SMS invite), `POST …/:id/request-changes`, `POST …/:id/reject`, `POST …/:id/approve` (zone + `max_active_orders` in the body; creates the `DeliveryPartner` and writes status history in one transaction).
20. **Screening checklist enforced on the server.** The review screen gates "Approve & activate" on six ticks (phone OTP, name/photo match Aadhaar, licence valid for two-wheeler, RC matches vehicle number, background check, safety briefing) — that is client-only today. Needs the checks stored per application (who ticked, when), `approve` rejected with 400 until all six are done ("Phone verified by OTP" is set automatically at sign-up), and an onboarding record (submitted → documents verified → checklist completed → activated, with the admin's name) for the partner detail page. Existing status history covers activate/suspend only.
21. **Documents: upload, verify, view.** No upload or storage exists. Needs types `PHOTO`, `AADHAAR`, `DL`, `RC`, `PAN` (PAN optional; cycles need no RC/DL), status `NOT_UPLOADED` | `UPLOADED` | `TO_CHECK` | `VERIFIED` | `REJECTED`, a 5 MB limit and jpg/png/pdf only (checked server-side), the number entered by the applicant vs. the number read from the document, licence expiry, masking (Aadhaar last 4, PAN tail), short-lived signed URLs for the review screen's preview, `POST …/documents/:type/verify` and `…/request-reupload`, and "replace sends it for re-verification". Needs a decision on where files live and whether identity numbers are encrypted. Also feeds the "4 / 5" docs column in the applications list.
22. **Partner sign-in, role and identity linkage.** There is no partner login. Needs OTP login for partners (reuse the phone-login flow), a `DELIVERY_PARTNER` role in the auth-service, delivery-service and gateway roles files, and the link `DeliveryPartner.user_id` ↔ the auth user. delivery-service's `authenticateToken` currently accepts only ADMIN / SUPER_ADMIN / OPS_STAFF, so a partner token would be rejected on every route, including the existing `/handle-orders/partner/handover/:id/confirm-*` ones. Self sign-up must create a user + application without activating anything.
23. **PARTLY DONE (2026-10-15) — `GET /delivery-partners/me` is built** (profile, vehicle, zones, capacity, `is_online`, 7-day delivered / failed counts; no on-time rate, since nothing records the promised time). Still missing: the online / offline toggle endpoint (the `is_online` and `online_since` columns exist), live-location sharing, vehicle-change request. Original note: needs `GET /delivery-partners/me` (profile, vehicle, zones, joined date, capacity), an online/offline flag with `online_since` (the model only has ACTIVE / SUSPENDED / INACTIVE, which is the *account* state), a live-location sharing toggle (`PATCH /:id/location` exists but is admin-only and nothing records "sharing off"), and a vehicle-change request (the Profile "Edit" / "Request change" buttons). "Updated 20 s ago" can come from `last_location_update_at`.
24. **PARTLY DONE (2026-10-15) — built:** `GET /delivery-partners/me/assignments` (ACTIVE / HISTORY / one finished status, `date=today`, paging), `GET …/assignments/:id` (order lines, timeline, customer phone while the job is open) and `PATCH …/assignments/:id/status` (PICKED_UP → OUT_FOR_DELIVERY → DELIVERED, or DELIVERY_FAILED with a reason). Details in `DELIVERY_PARTNER_MODULE.md`. Still missing: slot / due time, distance / ETA, payment mode and order total, packed state per line, masked customer phone. Original note: partners need `GET /delivery-partners/me/assignments?status=active` returning, per assignment: order id, slot and due time, store name/address/contact, item list with quantity and packed state, customer name, masked phone and address, distance/ETA, payment mode (paid online vs. cash to collect) and order total. They also need the status moves they make themselves: confirm pickup, out for delivery, delivered. The existing `POST /handle-orders/assignments/:id/update-status` is dispatcher-only.
25. **Delivery code (proof of delivery).** "Complete delivery" asks for the customer's 4-digit code. Needs a code generated per order and shown on the storefront order screen, `POST …/assignments/:id/deliver` that verifies it (rate-limited), "Resend by SMS", an optional doorstep photo upload, and the delivered-at time so "13 min ahead of slot" can be computed. The client currently accepts any 4 digits.
26. **PARTLY DONE (2026-10-15) — a failed drop writes a `DeliveryAttempt` row** (attempt number, free-text reason) in the same transaction as the status change, for the partner and the dispatcher path alike. Still missing: the reason enum, the attempt cap, the store notification. Original note: `DeliveryAttempt.failure_reason` is a free string with no attempt cap. Needs `POST …/assignments/:id/failed` with a reason enum (`CUSTOMER_NOT_REACHABLE`, `NOT_AT_LOCATION`, `WRONG_ADDRESS`, `REFUSED`, `OTHER` — remarks required for OTHER), the attempt number ("1 of 3"), and a notification to the store so it can reschedule or reassign.
27. **Partner-initiated handovers.** Only a dispatcher can start one today (`POST /handle-orders/assignments/:id/handover`). Needs partner-side `POST /handovers` (order, receiving partner, reason, meet point), `GET /handovers?direction=incoming|outgoing`, a decline endpoint, the timeline timestamps (request sent / old partner confirmed / receipt confirmed — only `old_partner_confirmed_at` exists), and `GET /delivery-partners/nearby` for "Nearby partners in your zone" (distance from last location, active / max). Only orders already picked up may be handed over.
28. **PARTLY DONE (2026-10-15) — the partner's history is `GET /delivery-partners/me/assignments?status=HISTORY`** (finished work, newest assigned first, last failure reason, per-order timeline in the detail call). Still missing: date range / search filters, per-status counts, handovers given / received, on-time rate, and the admin `…/:id/stats` and `…/:id/assignments`. Original note: needs `GET /delivery-partners/me/history?status=&from=&to=&search=&page=` (completed time, status DELIVERED / FAILED / TRANSFERRED / CANCELLED, attempts, note) with per-status counts for the range, a per-order status log, and 7-day stats for the partner Profile and the admin detail page: delivered, on-time rate, failed attempts, handovers given / received. For admin: `GET /delivery-partners/:id/stats` and `…/:id/assignments?status=active` (also feeds the "Reassign" link and reassigning orders on suspend).
